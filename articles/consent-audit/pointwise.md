# 同一句前提和假设，推理器能只看这一题吗？

在 GLUE 的 277 道自然语言蕴含题中，我们让同一份量化模型回答同样的前提与假设，只改变计算机怎样把题目组批。普通八条组批改变了 9 道题的二元判断，**9 道全从错变对**。随后把模型封装成一个仍接受批量输入、在内部逐题裁剪并计算的 ONNX 文件。无论按原序还是重新组批，它在每一题的三个原始分数都与单例逐位一致，准确率也从普通八条组批的 203/277 回到单例的 194/277。[逐题原始分数](rte-point-logits.tsv) · [锁定的蕴含任务复核口径](https://github.com/shuimo233/research-notes/blob/9cd0f352585cfa62dd69c94b4771410b9d08c60a/articles/consent-audit/rte-separability-protocol.md)

这给“只应根据相关理由作判断”提供了一个可执行版本。假定每道题由一对前提与假设完整指定，把一道题放到不同位置、换掉同批其他题目时，该题的输出应保持一致。这是一条关于计算行为的要求。它能做到何种数值精度，和答案能得几分，可以分开验算。

## 从真实评论中定位变化

前一项研究发现，GoEmotions 同一 INT8 部署有 465 条评论换了细标签。为区分哪些条件起作用，我们在运行两个中间对照前公开了约定。在全部 5,427 条官方测试评论上，对每条依次构造了四份合法输入。[原部署结果](go-model-ranking.md) · [先于中间条件运行公开的约定](https://github.com/shuimo233/research-notes/blob/2400691205d6a5aa7a17d3707a589793f9c7e052/articles/consent-audit/go-separability-protocol.md)

| 状态 | 调用方式 | 相对上一行，细类集合改变的评论 | 粗类集合改变 | 第一选择改变 |
| --- | --- | ---: | ---: | ---: |
| S | 单例，保留本条实际长度 | — | — | — |
| P | 单例，右补齐到本条所在真实批次的最大长度 | 314 | 266 | 198 |
| R | 在 P 的宽度内用同一条填满原批，读回原槽位 | 0 | 0 | 0 |
| M | 同一形状、长度与槽位，恢复原批中的其他评论 | 458 | 402 | 286 |
| S 与 M 的端点比较 | 单例与普通八条组批 | 465 | 417 | 287 |

P 到 R 在这批输入上的 151,956 个 float32 输出也逐位一致。R 到 M 只替换其余槽位的自然文本及相应掩码，所有目标行的实际输入都保持不变。沿预设路径，一共有 607 条评论曾换过细类集合，其中 **142 条后来恢复到最初集合**。两端对比会遗漏这 142 条；直接把 314 和 458 相加又会重复计数。源图中有 98 个逐张量动态量化节点，算子规范和实测均容许样本间的数值影响。这里的逐项对照只定位到受控的输入变化，没有定位到哪一层的哪个值。R 各克隆行也逐位一致。[四状态逐条档案](go-point-decisions.tsv) · [各步原始分数差异及摘要](go-point-logit-checks.json) · [ONNX 算子规范](https://onnx.ai/onnx/operators/onnx__DynamicQuantizeLinear.html)

在实际标签任务上，S、P、R、M 对原发布粗类参考的 micro-F1 依次为 0.668565、0.667931、0.667931、0.670402。换用“先在每人内部归类、再要求两人支持”的参考时，相应数值为 0.656321、0.657182、0.657182、0.659345。即便只看补齐这一步，两种参考对得分变化的方向也有不同判断。粗类映射、评审的两种含义及完整计分都沿用已公开版本。[按两套参考的分子分母与全部翻转路径](point-results.json)

## 用一份文件承诺逐题计算

把现有单例模型记作 f。对第 i 行，掩码为一段 1 后跟一段 0，长度为 ℓᵢ。导出器生成的模型对该行计算 f(idsᵢ[:ℓᵢ], maskᵢ[:ℓᵢ])，最后按输入顺序排列各行输出。实现使用无跨行状态的 ONNX Scan，循环体裁剪单行、恢复单例批维、执行原模型、移除单例批维。原模型权重不需要重新训练。GoEmotions 图的 1,038 个原运算与 516 个初始化张量、RTE 图的 732 个原运算与 184 个初始化张量，都经独立程序核对。[导出器](go_scan_export.py) · [图结构核对](point-checks.json) · [ONNX Scan 定义](https://onnx.ai/onnx/operators/onnx__Scan.html)

按这个定义，其他行既不提供本行的 token，也不能改变本行的有效长度或计算体。对确定的单例函数，集合增删与排列只会增删与排列相应的输出。实际运行时可能对嵌套子图采用不同的算子融合和浮点路径，因此还要核对数值。GoEmotions 按原序八条和按 ID 哈希顺序八条运行，**每种组序的 151,956 个分数均与单例逐位相同**。RTE 的两种组序也各自匹配全部 831 个分数。这是锁定模型和环境上的实测；数据类型、执行后端或优化器变化时可以复用同一检查。[原始浮点摘要](go-point-logit-checks.json) · [RTE 的 float32 十六进制记录](rte-point-logits.tsv)

在 GoEmotions 上，我们用同样的 128 条评论做了三轮顺序轮换的暖机计时。普通单例、普通八条组批、Scan 八条组批的中位模型调用时间分别是每条 **8.60、7.57、8.33 毫秒**。这里只测 CPU 执行模型，排除分词与创建会话的时间。Scan 保留批量调用接口，内部仍逐条计算；本机实测比普通八条组批慢约 10%。墙钟时间受机器与负载影响。[每一轮时间](go-point-timing.json) · [计时代码](go_context_time.py)

## 迁移到需要判断蕴含关系的任务

第二个模型是基于 DistilBERT 的三分类 MNLI 量化模型，与前面的 RoBERTa 情绪模型分别发布。将它用于 GLUE RTE 的二元判断时，取最大 logit 所对应的类别，ENTAILMENT 计为蕴含，NEUTRAL 与 CONTRADICTION 合并为非蕴含。我们在推理前固定该规则。原始 RTE ZIP 与 NYU 分发的验证 Parquet 在全部 277 个键、前提、假设和参考标签上相符；它们是同一批原始题目的两个发布格式。没有截断任何句对。[GLUE 来源](https://openreview.net/forum?id=rJ4km2R5t7) · [RTE 发布文件](https://huggingface.co/datasets/nyu-mll/glue/tree/bcdcba79d07bc864c1c254ccfcedcce55bcc9a8c/rte) · [独立模型发布者](https://huggingface.co/Xenova/distilbert-base-uncased-mnli)

| RTE 部署 | 相对单例，三分类改变 | 二元蕴含判断改变 | 二元判断答对 | 相对单例，有差异的 float32 数 |
| --- | ---: | ---: | ---: | ---: |
| 原模型单例 | 0 | 0 | 194 / 277 | 0 |
| 原模型、自然顺序八条组批 | 13 | 9 | 203 / 277 | 831 / 831 |
| 封装、自然顺序八条组批 | 0 | 0 | 194 / 277 | 0 / 831 |
| 封装、哈希顺序八条组批 | 0 | 0 | 194 / 277 | 0 / 831 |

例如第 66 题的前提描述了有没有天然温室效应时地球温度的差别，假设问这种效应是否改变全球气候。公开标注为蕴含。原模型单独读题时选了中性；在普通批中转为蕴含；封装后两种组序均回到中性。这一例既能用来发现其他题目影响了本题，又显示仅仅消除这种影响无法保证得到参考答案。九次由错变对是这个固定开发集的事实，数据未给出新数据上的正确率变化。[逐题记录与三类分数](rte-point-logits.tsv) · [完整计数](point-results.json)

## 查新与可以归属的结果

Microsoft ONNX Runtime 的 2021 年记录已经实测同句在不同补齐宽度下的量化变化。Kasa、Kasa 和 Negi 已在 2026 年对文本分类器直接研究相同形状下更换组内样本、不同补齐及量化的影响。逐样本处理或固定量化尺度均有先例，无状态扫描和逐元素映射也是现有计算工具。因此本项工作的归属限于固定模型和数据的四状态外部复现、142 条中途翻转后恢复的实际记录、可重新生成的两份图，以及在自然语言蕴含上“全部分数恢复、答对少九道”的实证。检索未发现针对这两份图和这些官方记录的同一份逐项报告。不能据此确认全球首创或推断开放式推理能力提高。[直接先例与逐项查新](go-context-prior.md) · [2021 年的运行记录](https://github.com/microsoft/onnxruntime/issues/8625) · [Kasa 等原文](https://arxiv.org/abs/2610.09111)

## 怎样使用

已有锁定源图时，在本目录执行以下命令可以重新生成 GoEmotions 封装文件。对 RTE，将两个路径换为对应图，并追加 `--sha256 5b7e374d8d1e44149fafa498efe80166f740914b3e53bcfa6115fb3ecaca0945`。两份原始图都是 opset 11。导出器支持具有动态序列宽度、两个 int64 输入 `input_ids`、`attention_mask` 和一个定长 float32 logits 向量的确定性、无嵌套子图分类器；另有 opset 11、12、13、18 的小图回归。新模型仍需与其原单例对照。词表范围和最大有效长度沿用原模型，入参须为非空二值右补齐掩码。[运行接口](point_runtime.py) · [边界与结构检验](point_check.py)

```sh
uv run --no-project --python 3.13 --with onnx==1.19.1 --with numpy==2.3.3 -- python -I -B go_scan_export.py go-onnx/onnx/model_quantized.onnx go-point.onnx
```

```python
from pathlib import Path
from point_runtime import make_session, batch_logits

session = make_session(Path("go-point.onnx"))
logits = batch_logits(session, input_ids, attention_mask)
```

上述两个数组由原分词器产生，形状为“批大小 × 补齐后宽度”。运行接口在进入图前检查右补齐合同；直接使用 ONNX 文件的调用者需做到同一项检查。模型权重留在原发布处。完整下载、复算和核验命令见[复现实验说明](point-reproduction.md)。
