# 先核对来源，还是再读一份报告？

2026-11-23

四份报告依次写着“请求、请求、未请求、未请求”。最多一个记录器可能失实。如果只有前两份是同一应用日志的导出，这四份报告按三个采集根计为一票请求、两票未请求。如果只有后两份共享授权回调记录，按根计则为两票请求、一票未请求。每张来源图单独都能给出确定判断；两张图同时可能时，完全相同的行为日志容许相反结论。

我们用两个实际模型产生了这两种情况，并做了一个混合审计器。它既可以买一份行为记录，也可以买一条可信的同源核验结果，每次读完再决定是否继续。输入要求显式给出可能的来源图。核验通道必须能可靠地告诉审计器两个报告是否出自同一采集根。[标准库工具](lineage.py) · [实验口径](lineage-protocol.md)

## 一个值得临时改变查法的例子

假设同一事件已有两条相反的报告，来源关系有 P、Q 两种解释。现在可以读报告 a、b、d，分别花 7、1、5；也可以花 2 核对 d、e 是否同源。对全部可行真值、来源图及错误答复进行独立枚举，所得最坏费用如下。

| 第一项或策略限制 | 保证作出正确判断的最低最坏费用 |
| --- | ---: |
| 先读 b，之后可自由选择 | **8** |
| 一律先核对来源，之后自由选择 | 9 |
| 整个过程只读行为报告 | 12 |

先读 b 后，如果读到 0，有一条最优策略接着查同源凭据；如果读到 1，工具接着读 a。前一条路可能还需再查行为记录。数字来自一个刻意搜索并缩小的构造例，反映三种策略在**同一个输入**上的差别。[全部来源图、既有读数和价格](lineage-mixed.json) · [枚举结果](lineage-validation.json)

## 真实采集怎样得到同一组日志

沿用之前的八个合成示范，重新训练决策树和逻辑回归。未获同意、输入收益为 8 时，树拒绝，回归模型请求。在应用决定、工具入口、SQLite 授权回调三个位置采集，执行闸拒绝实际写入。树模型这一组令应用记录器错误报 1，将它复制为 a、b；回归模型那一组令授权回调记录器错误报 0，将它复制为 c、d。两组都真的产生了相同的四个归档位 `1100`，库中均没有新增记录。第五份可购行为报告 e 取自工具入口。

| 来源关系核验文件 | 第五份行为报告 | 工具实际选择 | 两次运行分别判定 |
| ---: | ---: | --- | --- |
| 64 B | 128 B | 读 64 B 来源核验文件 | 树未请求，回归模型请求 |
| 192 B | 32 B | 读 32 B 工具入口报告 | 树未请求，回归模型请求 |

归档程序按实际复制路径另存了 a、b 的根标识，所以这里可以核对来源。规划器只看到价格和付费后返回的位；读回时在夹具内核对摘要。两份内容一样并不自动证明同源。文件大小是实验设置，读取量为实际返回的逻辑字节，未计训练、建档及独立建立信任的费用。在外部系统上，这个保证还依赖真实映射列在输入中、登记的根对应实际故障边界、元数据核验通道可靠。[逐次读回数据](lineage-results.json) · [采集脚本](lineage_demo.py)

## 哪一部分有新的研究价值

第一轮查新就确认，询问“两对象是否同组”和在付费测试间主动选择都有先例。具体列出必须被某个故障根解释的记录之后，又遇到了更近的旧问题：**只有一个行为位和两张来源图时，判断两种相反解释能否共用完整记录，等价于给二分图分别用有限数量的行和列盖住出错单元**。这个覆盖问题早已用于芯片备件分配。[同簇查询](https://arxiv.org/abs/1606.02404) · [Kuo 与 Fuchs 的原始工作](https://doi.org/10.1109/MDT.1987.295111)

我们得到的窄结果有两部分。首先，即使增加“每张图单独都有超过两倍故障上限的不同来源、各自都能多数判别”这一保证，**两图合起来仍可能无法判别**；当允许的坏根数也是输入时，判断是否存在这种共同记录仍为 NP 完全。其次，有历史和多个情境时，可以消去未知的行为向量，把是否有相反解释写为“以下至多三个根中，至少一个失实”的一组约束。左右两个世界单独计故障数。这给出小故障数下的精确算法，并能恢复两张图、两种相反行为、各自的坏根与完整共同记录。有个局部实例确实需要三项才能用原来的根指标直接表达。以上复杂性和算法界针对菜单是否足以区分两种结论，最低费用策略单独求解。[归约与证明](lineage-proof.md)

独立验证器穷举了 **446 个输入、4,792 串完整菜单答复和 1,548 对有序来源图**，对照费用、首选项目或不可判定证书。另用 144 个小图与额度组合验证行列覆盖归约，在 256 个情境的例子中恢复出了一个涉及所有情境的非零证人。核验器针对小样例保证实现的一致性，一般结论由证明给出。[核验代码](lineage_check.py) · [机器输出](lineage-validation.json)

发布前又按相关噪声测试与代表族两个方向复查，包括上一轮的反例清单。一般的混合选题、行列覆盖和消元算法均归于已有工作。目前可供审查的是这项来源审计协议的具体归约、强多数限制和可运行证书；尚未确认全球优先权。[分阶段先例核查](lineage-precedents.md)

## 直接使用

将 `source_audit.py`、`lineage.py` 与需要的示例 JSON 放在一起。以下命令只用 Python 标准库。

```shell
python -I -S -B lineage.py lineage-mixed.json
python -I -S -B lineage.py lineage-mixed.json --record b 0
python -I -S -B lineage.py lineage-mixed.json --record b 1
python -I -S -B lineage.py lineage-ambiguous.json --feasibility-only
```

最后一条给出两种相反世界与逐项共同答案；保存为 UTF-8 JSON 后，可用 `lineage.py lineage-ambiguous.json --verify-witness 报告文件.json` 从原始输入直接核对。先判断能否区分的模式适合显式候选图和较小故障额度；精确费用搜索随菜单项数最坏呈指数增长。[不可判别示例](lineage-ambiguous.json) · [按查阅价选择文件的示例](lineage-example.json)
