
# 冻结协议：减少共用档位数能否降低实际执行耗时？

复用上轮 SNLI 选题、同一 INT8 CPU ONNX 模型和八档最小补齐宽度。已发布分数与三实况分组的 Git 对象分别为 09efe9dbdb03c0826bfc884e6cc2228ebbd551b8 和 06cc9ac4fa4c04dff0b840475c5c0a34c3be5595。所有执行方式必须逐位重现按请求单独执行、保持其所选最小补齐宽度的 float32 分数。

## 运行方式

在原有 ONNX Scan 单例语义上，最小补齐宽度作为每行输入。每行先按掩码取有效前缀，再补到所请求的最小宽度，与同批其他请求的宽度无关。固定同一 CPU 会话、四线程、一个调用线程。将相同会话用于两种调用形状。

- 按有效宽度分桶。一项的有效宽度是实际词元数与请求最小宽度的最大值。同一有效宽度一次调用。
- 单次打包。整批一次调用，每行携带各自最小宽度。

计时之前，对所有 1,440 个方向和八档做逐位语义核验。使用同一目录与档位组的场景，对每条记录以规则 (目录号 + 请求槽位 + 实况编号 + 外层档位编号) 模八选择行档位。八次对照覆盖每题全部档位，也使大部分批次包含不同最小宽度。

## 匹配输入与计时

固定第 0、12、24、34、48、59 号目录及三个实况。分组取零分差门槛的冻结证书。预定种子 7340826，做两轮。每个目录和实况每轮生成 16 个批次，前八批在两种调度中使用完全相同的逐项档位排列。后八批分别使用逐项随机排列和每个已审组共用随机排列。每个请求在每种调度的每轮恰好用每档两次。排列只用于隔离有限样本中的逐题输入差异，单批的架构保证沿用已声明的独立选档规则。

四种组合为两种调度乘两种调用方式。在同一批次单元内轮换执行顺序。每轮以纳秒记录从准备数组到得到原顺序分数的墙钟时间，含数组构造、参数核验、ONNX 调用和组结果回填。排除分词、加载模型、预热、抽签准备、文件写入及计时后的逐位比较。四种方式提前各预热一次。记录名义档位种数、有效宽度种数、调用次数、有效宽度和及平方和。保留每批原始计时与可重算汇总。

主要比较为各执行方式内分组调度相对逐项调度的时延。两轮的成对时延比例中位数都至多 0.95，且对应两轮第 95 百分位的时延分别至多是对照的 1.05 倍，才判定该方式达到预设收益。分别报告单次打包相对分桶的同类数据。计时在同一主机完成，以暂时的运行环境为边界。模型语义和匹配输入可逐位复核，墙钟测量允许重新运行后变化。
