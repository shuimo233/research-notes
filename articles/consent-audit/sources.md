# 两份日志，几个证人？按来源核验代理行为

2026-11-23

在同意审计里，应用日志和它的导出报表都说代理没有请求写入，工具入口却说代理请求了。两票对一票，该信谁？

我们用重新训练的逻辑回归模型实际跑了这个情景。它在没有得到同意时，面对收益 8 和 20 都请求了写入。我们只让应用记录器漏记，再原样复制它生成的文件。把导出误标成第三个来源，工具会得出错误的“两个条件均未请求”；标回真实来源，工具会给出两种完全能解释现有记录、结论相反的情况。再从 SQLite 授权回调取得一份 64 字节的记录，就足以确认至少请求过一次。执行闸在两次试验里都拦住了写入。[原始读数、实际读取量及两种解释](source-results.json)

## 一条读数为何能解决两档分歧

假设在整个试验期间至多有一个采集来源会报告错误，该来源可以在多条记录里持续出错。每个情境的真实请求行为保持稳定。应用及其导出在两档都报 0，工具入口在两档都报 1。

| 可能的实际请求 | 必须有问题的来源 |
| --- | --- |
| 两档均未请求 | 工具入口 |
| 两档都请求 | 应用记录器，含由它生成的导出 |
| 只在一档请求 | 应用和工具入口都得有问题，超出额度 |

所以两档的真实行为虽未确定，却已经知道它们一定相同。再看独立采集位置的任意一档就能分开两种解释。这里无需预先赋予第三个记录器更高信誉：两种解释各自都已用掉唯一允许的故障来源。在模型中，它在这两种解释下都必须如实报告。

这个现象可以扩展到 512 档乃至更多。一个根处处报 1，另一个处处报 0，在至多一个根会失实时，**即使所有“只在某一档请求”的解释都被排除，也仍可能每一档都请求过**。所以，上轮按试次计错时成立的单点结论，换成按来源计错就会误判。程序在 512 档用例中构造出了两个相反解释，并验证增加一条新根观测即可判定。[验证记录](source-validation.json)

## 哪些反例值得保留

对每个报过 1 的来源，记下它在哪些情境报过 1。只要全零仍能解释历史，为判断某一份核验菜单能否区分全零与非零，工具只需检查两类候选：每一个单独情境，以及若干来源各自报过 1 的情境集合之并。

若有 $n$ 个情境，历史里有 $a$ 个来源报过 1，这份清单至多有 **$n+2^a-1$ 项**，即使可能的非空行为有 $2^n-1$ 种。全零相容时 $a$ 至多等于允许故障的根数 $f$。当 $f=1$ 时，单点之外最多再检查一个整体反例，这个反例本身可以覆盖全部情境。

我们也得到了这个上界的匹配下界。对同一段历史，若必须**提前列出完整反例，供任意未来核验菜单使用**，那么在 $a=f$、$n\ge2f$ 的最坏情况下，清单少一项就会答错某份菜单。证明对每一项都构造了让它成为唯一有效反例的菜单。这个界衡量的是显式清单长度；它不限制其他算法用更短的符号公式描述候选，也不等于付费查询决策树的运行时间。[上界、紧例与适用条件](source-proof.md)

## 原型与实际读数

输入包含情境、档案名对应的采集根、最多允许几个根出错、已有读数，以及每份待查记录的情境和费用。工具先判断现有证据；若还有歧义，它会给出以下两种东西之一。

- **最低最坏费用及下一份记录。** 在读到相应位之后重新求解，可继续采购最划算的证据。重复查询同一根同一情境无法保证进展；同一根在此前没测过的情境仍可能提供有价值的信息。
- **一份可独立重算的不可判定证书。** 列出全零与非零两个世界、两边哪些根必须有问题，以及即使查完整份菜单也可能读到的同一串答案。接收方能直接核对证书，不用再搜索决策树。若历史已经与整个模型矛盾，工具单独报告。

实验在应用决定是否调用、工具函数被调用、SQLite 授权回调收到 INSERT 三个位置分别采集同一试次的请求位；回调实际拒绝操作，另开连接核对表内行数。故障仅注入归档读数，不改变模型执行。下表统计审计阶段追加核验的逻辑字节，历史读取、训练和建档不在这个费用里。三个位置位于同一个本地进程，实验证明本夹具中注入一个通道故障时的结果；部署中若共同上游能同时破坏多个通道，就要按实际故障关系定义根。

| 运行 | 只许再读应用导出 | 加入授权回调后的实际结果 | 追加读取 |
| --- | --- | --- | ---: |
| 决策树，正常采集 | 已知两档均未请求 | 相同，直接停止 | 0 B |
| 逻辑回归，正常采集 | 已知至少一档请求 | 相同，直接停止 | 0 B |
| 逻辑回归，应用记录器漏报 | 两种解释都成立 | 确认至少一档请求 | 64 B |
| 逻辑回归，工具入口记录器漏报 | 两种解释都成立 | 确认至少一档请求 | 64 B |

每组均使用两个实际收益 8、20 的无同意事件，数据库成功写入均为零。完整输入另含较贵的 128 字节授权回调记录；一份 64 字节的核验已达最坏费用下界。归档大小是实验设置，读取量来自所选文件。[采集与读回脚本](source_demo.py) · [四组轨迹](source-results.json)

## 如何核查与复用

小域对照没有用清单公式生成答案。它枚举每个真实行为和完整的未来报告，再从全部合法报告搜索最优决策树。在 **477 个输入**上核对了可判定性、最优费用、首选记录或不可判定证书，涉及 5,664 串完整菜单读数。另对 $f=1$ 至 5 的下界构造逐一枚举真值，验证同一份历史中的各目标确实能成为唯一反例。$f=5,n=10$ 时共有 41 份这样的菜单。[独立验证器](source_check.py) · [机器输出](source-validation.json)

将 `source_audit.py` 与 `source-example.json` 放在同一目录。首条命令会从费用 1 的导出、费用 3 和 7 的两份新根观测中选择 `verify-low`，最低最坏费用为 3。第二条录入这份记录为 1，结论变为 `some_request`；改为 0 则是 `all_zero`。

```shell
python -I -S -B source_audit.py source-example.json
python -I -S -B source_audit.py source-example.json --record verify-low 1
```

另一个[单情境样例](source-copy-example.json)能直接生成不可判定证书。将其中唯一一条历史的来源从 `application` 改为 `gateway`，其余不动，现有菜单就能保证判定。这两种情况的差别只在于过去那条证据来自哪里。

大菜单可用 `--feasibility-only` 先判定现有覆盖是否足够，跳过费用树。对于输出为 `unidentifiable` 的场景，可以将报告保存为 UTF-8 JSON，再用 `source_audit.py 场景.json --verify-witness 报告.json` 核对整份证书。费用求解最坏随待购的不同“根、情境”组合数指数增长，适合小菜单。[标准库工具](source_audit.py) · [可修改的输入](source-example.json)

已有研究解释了复制来源为何会误导多数判断、受损传感器应按来源计数，以及怎样用冲突报告定位一组可能的故障部件。这里提交审查的候选原创结果，是**对来源可能整体失实的全零判定，给出菜单无关的显式反例清单，并证明它的最坏大小可取到**。本轮未找到直接陈述这一上下界的原文，优先权仍待核实。工具假定已知档案怎样追溯到采集根；在来源关系未知的系统里，自动找出真实依赖是另一项任务。[对应原文及查新边界](source-precedents.md) · [实验口径](source-protocol.md)
