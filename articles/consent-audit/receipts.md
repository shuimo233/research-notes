# 同一份日志，两种相反的行为，归档时还要留几位来源信息？

2026-11-23

如果检查的位置也可以改，后续结果给出了每种补充位数下所需的最少检查数。[归档格式的精确取舍与构造工具](receipt-frontier.md)

我们让两个模型在未经同意时决定是否请求一次 SQLite 写入。逻辑回归模型请求了，决策树没有。两次归档读出来却完全相同：先是 11 个 0，再是 21 个 1。连那条事先保留的同源检查也给出了相同答案。接收方靠什么分清两次行为？

这取决于 32 行记录背后有几个证人。实验中只有三个采集位置，每个位置的一次观测被忠实地复制到一段相邻的行。对逻辑回归，三段分别长 11、12、9，两段报 1；对决策树，三段长 9、2、21，两段报 0。第一种情况下，第 11 行后是真实的**第一个**分界；第二种情况下，同一个地方是**第二个**分界。两次各有一个记录器被实验程序故意翻转。SQLite 均拒绝实际写入。[两次采集的读数、切点、模型与故障位置](receipt-results.json)

## 已有同源检查，最少还需补几位

假定归档方事先知道两个分界，每次事件都用同一套来源布局，接收方事后读日志时已经离线。我们给出一个公式：输入日志可能分界的位置，以及档案已经保存的任意一组同源检查，就能直接算出，为了永远判断对三根多数，归档方**最少还要预留多少种标签、多少位**。可以同时构造达到这个下界的编码。

例如有 31 个候选切点，档案已记录“第 1 行和第 16 行是否来自同一根”。这相当于已经知道前 15 个位置里有没有切点。前 15 个位置同属一类，右侧还有一个可能的另一端；后 16 个位置同属另一类。两类各自最多要在 16 个有序位置上判断端点的先后。精确答案是 **4 种标签，刚好 2 位**。实际两次归档的标签分别是 2 和 1，由此解出了相反的请求行为。若要记全两个分界，共有 465 种布局，固定宽度需 9 位。若档案没有已有同源检查，专为该判断准备的最短标签为 3 位。[公式、上下界与解码规则](receipt-proof.md) · [可直接解码的归档样例](receipt-example.json)

这个问题与已有研究接得很近。只给两个有序元素编码，日后对一个保证在其中的元素回答它的秩，正是两键的**单调最小完美哈希**。它的冲突图和色数都有先例。本次推导处理了另一种常见的工程约束：档案格式里已经有一些同源检查，补充字段必须与它们合用。区间的连续性保证，一旦两个候选布局还会产生歧义，共享的那个切点必须独自解释整组检查答案。按这条性质拆开冲突图，每组只剩三个数需要计算：该签名出现几次、左侧和右侧是否各还可能有另一端。中英文定向检索尚未定位直接给出这一剩余容量公式的公开文献。[单调最小完美哈希原文](https://arxiv.org/pdf/2207.10556) · [区间组测试原文](https://doi.org/10.1504/IJBRA.2005.008441) · [先例核查记录](receipt-precedents.md)

## 证明之外，归档真的省下了什么

我们先在本机为 32 个布局各建三个根文件，再用硬链接生成有序的导出行。登记程序在模型行动**之前**向文件系统核验文件身份，并把来源字段打包写盘。之后在应用决定、工具入口和 SQLite 授权回调三个位置实际采集行为，将每个布局指定的一根记录翻转。离线解码器只拿到归档的行和登记字段。硬链接保证这次实验里确实是同一份根记录的副本。[实验脚本](run_receipt_demo.py) · [Python 的文件身份检查](https://docs.python.org/3/library/os.path.html#os.path.samefile)

| 32 个布局的归档方案 | 实际写入并读回的来源字段 | 128 个事件的结果 |
| --- | ---: | --- |
| 复用已有的 1 项同源检查，再补最短字段 | 已有 4 B，新增 **8 B**，合计 12 B | 全部正确 |
| 从头只发最短的专用标签 | 12 B | 全部正确 |
| 存下完整切点布局的编号 | 36 B | 全部正确，还能恢复完整布局 |
| 仅使用预先固定的同源检查 | 64 B | 全部正确，16 项检查已达该约定下的最小数 |
| 按导出行数作多数表决 | 0 B | 错 28 次，平票 0 次 |

这些字节仅计跨布局紧凑打包的来源字段。原始行为数据、文件系统元数据、认证和归档索引另计。实验实际执行了 128 个模型决策，其中 64 次提出写入请求，成功写入 0 行。这些决策来自两个模型、两种输入的重复采集，不能当作生产错误率。若登记方始终在线，经证明每个布局一生最多再问一次即可；这个强对照在 32 个布局合计只问了 21 次，也全部判对。离线交付是预存标签值得付费的前提。[实测结果](receipt-results.json) · [固定与在线查询的证明](receipt-proof.md)

独立测试从三个根的八种可能读数生成原始日志，再对产生冲突的布局做精确图着色。2,002 组检查菜单、8,702 组已有答案的最少标签数均与公式一致，178,520 次解码全部匹配原始三根多数。另一个仅有三项预设检查的配置包含 10¹⁵ 个候选切点，建表只需处理五段常签名区间；这项检查仅验证建表规模。[独立核验程序](run_receipt_check.py) · [全部核验计数](receipt-checks.json)

## 复现与适用边界

在 `articles/consent-audit` 下运行。前两条只用 Python 标准库。第一条应返回 `root_majority` 等于 1；把样例的 `tag` 从 2 改为 1，则相同日志返回 0。第三条需要支持硬链接的本地临时目录。

```sh
python -I -S -B run_receipt.py receipt-example.json
python -I -S -B run_receipt_check.py
uv run --no-project --python 3.13 --with scikit-learn==1.8.0 -- python -I -B run_receipt_demo.py
```

计算自家格式的字段宽度，只需传入形如 `{"n":31,"intervals":[[1,15]]}` 的 JSON 文件。加上 `"cuts":[11,23]` 可签发该布局的字段。登记人与审计人要使用同一个有序布局和检查表。工具假设归档元数据可信，三个连续段代表三个不同根，各段以同一次观测为源，每次事件至多一根失实。副本被独立编辑、根出现顺序交错、两个探针因共享故障而一起报错，均超出这份保证。在外部日志平台是否满足这些条件还需实测。[实验口径](receipt-protocol.md) · [工具源码](run_receipt.py)
