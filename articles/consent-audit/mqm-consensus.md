# 两位专家都说有严重错误，他们需要指出同一种错误吗？

一份译文有两条严重错误标注，一条是误译，一条是漏译。如果两条来自同一位评审，就只有一人报告了严重错误。如果来自不同评审，就有两人。WMT 发布的中英译文中能找到这两种情形，甚至能找到来自同一系统、各项汇总数字完全相同的一对。本研究问的是，想让后来的人还能判断“至少两人各自报告了某种问题”，存档时究竟要留下哪些信息。[WMT 原始数据](https://github.com/google/wmt-mqm-human-evaluation/tree/29acd6999aaea3586378c9dcb58d8cc4820cede3/newstest2020)

## 一对能逐条核对的真实记录

`Human-A.0` 是 WMT 中英数据中的人工参考系统。第 238 和第 706 段的官方均分都是 −3.366667。下面这张表对两段都成立。

| 严重度和类别 | 标注条数 | 报告该项的不同评审人数 |
| --- | ---: | ---: |
| 严重，误译 | 1 | 1 |
| 严重，漏译 | 1 | 1 |
| 轻微，标点 | 1 | 1 |
| 无错占位 | 1 | 1 |

回到原始记录，第 238 段的两条严重问题来自**同一人**，第 706 段来自**两个人**。两段均有三位评审。即便知道每一行各有几人支持，只要忘了跨行是不是同一个人，就无法同时答对这两个问题。另一对中英实例发生在 `DeepMind.381` 第 140 和 699 段。两段各有三人报告严重问题，均分同为 −6，逐类统计也相同。后来若改问“是否有两人分别报告了轻微误译或轻微语法问题”，答案依次为否、是。只保存最初那一道严重问题的答案也会丢掉东西。[复核集原始键、查询与逐项统计](mqm-zhen-results.json) · [独立 SQL 复核程序](mqm_reference.py)

## 从哲学问题到可检验的规则

判断聚合文献早已区分了“分别对理由表决”和“对每个人据此得到的结论表决”。List 举过自然保护区的例子，人们可能各有不同理由支持保护，却无法让任何一个具体理由单独赢得多数。译文例子里，理由换成了记录中的错误类型。我们采用这个已有区分，把它落实成可以从原始记录独立求值的三个问题。未标出的类别只表示这位评审没有记录它。[List 的原文，第三个例子及两种表决程序](https://eprints.lse.ac.uk/5829/2/The_discursive_dilemma_and_public_reason_%28LSERO%29_.pdf)

| 判定为“是”的条件 | 英德开发集 | 中英复核集 |
| --- | ---: | ---: |
| 至少两人标过同一细分类别的严重问题 | 1,185 | 7,804 |
| 至少两人标过同一顶层类别的严重问题 | 1,233 | 8,281 |
| 至少两人各自标过任意严重问题 | 1,420 | 9,202 |

顶层类别按 WMT 标签第一个斜线前的部分确定，例如误译和漏译同属 Accuracy。这里的同类不要求标注同一文本跨度。英德有 235 份、中英有 1,398 份译文满足第三行但不满足第一行。中英的差额里，477 份在顶层类别上仍能取得多数，921 份连顶层类别也各不相同。这三项比较是在主结果揭晓后补做的，同一套按人分组的 Python 计算与另一套直接读 TSV 的 SQL 查询对每一份译文核对。[分系统计数](mqm-agenda-results.json) · [两套计算](mqm_agenda.py)

## 哪些判断已经能从现行汇总中恢复

主检验只问三人里是否至少两人各自标过译文 Major 错误。英德 14,180 份、中英 20,000 份是“某系统对某段的译文”；每个方向十个系统或人工参照共享一批源段，每份译文恰有三名评审。均分按原协议从逐条记录重新计算，34,180 份全部匹配到发布精度。原作者用均分描述错误负担。本研究的参照答案是评审实际记录的意见，同时保留多人对不同错误作出判断的可能性。[原始研究与评审协议](https://aclanthology.org/2021.tacl-1.87/) · [WMT 对均分表和逐评审表的说明](https://www.statmt.org/wmt21/metrics-task.html)

| 确定规则能看到的输入 | 英德至少答错几份 | 中英至少答错几份 |
| --- | ---: | ---: |
| 仅官方片段均分 | 744 | 1,626 |
| 均分和每类标注条数 | 28 | 160 |
| 均分、每类条数、每类不同评审人数 | 1 | 38 |

计算办法是按看得到的输入分组，在每组内数出“是”和“否”，取较小者，再求和。知道整批答案、为每组挑最常见的标签，就能恰好达到表中的数，因而它给出该语料上的精确最少错数。系统名、段号、正文均未提供给预测规则。在中英，最详细汇总仍留下 27 组内部意见相反的统计，涉及 103 份译文。另一个直观对照是让每条记录各投一票，含无错占位，平票单列。英德出现 907 个相反结论及 206 个平票，中英为 2,776 和 1,320。这里没有对未来语料的错误率作估计。[英德原表](mqm-ende-results.json) · [中英原表](mqm-zhen-results.json)

## 存档时可以具体怎么做

如果以后只查一个固定问题，存一个结果位就够了。若以后要自由选类别，例如把误译和漏译合并后再问，仍有一种小而精确的补充信息。先保存每类的标注条数和不同报告人数。任何已有两人报告的类别都能单独让查询通过。只出现于一人的类别，按“是否来自同一评审”分组。一个查询只要碰到前一类，或触及后一类中的至少两组，答案就是“是”。评审在别的段落是谁，对这道题没有作用。[可执行编码和解码](mqm_receipt.py)

给定这份公开汇总，如果三人记录可实现恰好 F 种不同的查询行为，独立存储该段时，固定宽度的补充字段最少需要 ⌈log₂ F⌉ 位。每两种分组总有一个单类或双类问题能把它们区分开。实现数出合法分组，为实际分组编一个号；人数、五行上限与独占标记都能排掉一些不可能的分组。在符合严格规则的 33,247 份译文中，18,705 份连一位补充信息都无需存储。[可行性证明、编号及限定条件](mqm-proof.md)

原始记录还暴露了一个容易忽略的设计选择。英德 583 份、中英 350 份至少有一人的行数超过五条，或同一人同时留下无错标记与其他行。我们保留这 933 份及其原始意见，并存储回退标记。这些是导出表的可观察性质，原因尚未查明。冻结版允许回退记录采用任意三份非空打分单；若标记的含义进一步保证“确实有一人违反严格规则”，事后验证显示，两种语言分别还能少用 270 和 87 位。这说明编码最优性依赖读者对每个字段含义的准确了解。[开发集更正](mqm-holdout.md) · [标记的精确重算](mqm-flag-results.json)

### 实际文件有多大

冻结版回读全部 34,180 份译文。已有逐类汇总和模式标记时，英德和中英任意类别并集所需的补充文件分别是 **1,811 和 3,515 字节**。用于回读的 JSON 行表包含键、逐类汇总及模式，另占 1,946,193 和 3,038,557 字节，还各有一份校验清单。若只需固定的 Major 判定，已有同一份汇总时，仍有余地的段分别只需合计 356 和 1,444 位。前述数字均针对冻结版。[存档工具](mqm_archive.py) · [证明与成本口径](mqm-proof.md)

| 新建档案保留的内容 | 英德原始 | 英德压缩 | 中英原始 | 中英压缩 |

| 一个预定多数答案 | 334,182 | 40,335 | 461,540 | 56,585 |

## 查新范围与可复现性

采用了已有的判断聚合理论、AIMS 的逐人逐类去重做法、投影计数与枚举编码。此次形成的候选贡献是 WMT 指定版本上的自然反例与精确计数，以及在这套三人审查约束下可回放、可计算最低补充位数的存档方法。直接用途是给质量复核队列或评测档案实现指定的查询语义。项目没有测量译者工作效率、专家的客观正确率或推理模型性能。独立实现针对的是软件核对；尚无项目外研究者的复现或使用反馈。优先权判断限于所列公开检索。[逐项先例与检索词](mqm-precedents.md) · [AIMS 原转换实现](https://github.com/aims-foundations/measurement-db/blob/7e223f127c76f7f049955730c3493345e330827d/benchmarks/wmt_mqm/build.py#L62-L76)

主问题和对照先于两种语言的多数计算公开。英德用于开发，看到真实异常后增加回退路径，再冻结实现，随后首次计算中英主结果。判断聚合的三层比较、四种完整格式、以及利用标记进一步缩小编码空间是在看到复核结果后增加的。两种语言来自同一轮 WMT；组内重复评价和文档共享评审均需保留在解读里。[公开检验口径](https://github.com/shuimo233/research-notes/blob/1b58465aaf049cd32a662d25280eda064161bd52/articles/consent-audit/mqm-protocol.md) · [中英运行前的实现](https://github.com/shuimo233/research-notes/tree/4cbb470069382b6fdb34dea4bf18a77f660f187e/articles/consent-audit)
