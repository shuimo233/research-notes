
# 组内分层抽档，能否消除长批次带来的尾部代价？

以前每个合规组只抽一档，组内的长任务容易同时出现。本轮把组内抽签改为跨档位分层，再把抽中的档位随机分给请求。**组间仍独立，任意窗口的归一全拒绝保证仍成立。** 两轮同一 CPU 会话的测试中，P95 耗时从原共用策略的约 75 毫秒降至约 49 至 51 毫秒。相对逐项独立抽签，尾部略有下降，配置节省和延迟改善都没有达到预先设定的 5% 主门槛。 [冻结协议](https://github.com/shuimo233/research-notes/blob/4028ecdd856ea72b084e609c2e3e6dc0dfa1e48c/articles/consent-audit/audit-runtime-strata-protocol.md)

## 哪些组内随机规则可以沿用证书

旧证书从请求对在任意共同档位分布下的兼容性出发。对每个已认证的组和任意子窗口，如果每个实况至多有一个随档位变化的拒绝率，归一倍率恒为一。否则，各实况中随档位变化的行拥有同样的比例类多重集。把各行拒绝率向量除以它在共同档位分布下的平均值，常量行就变成 1，彼此成比例的行也变成同一个向量。

只要组内档位向量的联合分布对请求位置置换不变，任一窗口的边缘分布也有这个性质。在两个实况之间重排这些归一向量只会重排一个期望乘积中的坐标，结果相等。不同组独立时，整窗归一倍率是各组结果的乘积。固定比例逐项独立的分支继续保留同样的边缘和概率下限。

公平的逐项档位分布本身不足以提供这个保证。独立检查器还验证了一个三档循环分配，两个实况的每项档位边缘都相同，交换两个条件向量后得到的归一倍率却分别为 \(156/133\) 和 \(123/133\)。 [证明、先例与边界](audit-runtime-strata-prior.md) · [完整概率表检查](audit_runtime_strata_boundary_check.py)

## 抽档时怎样防止整组抽到长档位

沿物理宽度顺序切分共同档位的累积概率。每层抽一档，复制给该层的请求份数，再把选出的档位均匀打乱。某项落入某层的概率等于该层的概率份额，合起来仍得到原始档位分布。均匀打乱使同组请求位置可交换。实验把组细分成二次幂大小的子组，每组最多四层，组间独立。可执行接口接受一份已认证的分组和按宽度排序的任意有理概率。 [调度实现](audit_runtime_strata.py)

计时用旧目录和六个未参与上一轮计时的新目录，全部三个实况。三种调度在每轮对每题使用每档两次。前半轮每批的档位向量也完全相同。后半轮分别采用逐项独立、组内共用一档和组内分层。新实验共 3,456 项，同一 CPU 会话、按实际有效宽度分桶，所有 **82,944 个分数**与对应单独执行时的冻结分数逐位一致。 [运行程序](audit_runtime_strata_run.py) · [独立复算](audit_runtime_strata_check.py)

## 实测结果和预设门槛

| 调度 | 第一轮 P95 | 第二轮 P95 | 两轮每批平均有效宽度数 |
| --- | ---: | ---: | ---: |
| 逐项独立 | 51.64 ms | 51.58 ms | 5.96 / 6.03 |
| 组内共用一档 | 75.05 ms | 75.69 ms | 4.60 / 4.63 |
| 组内分层 | 49.27 ms | 50.66 ms | 5.82 / 5.85 |

相对逐项独立，分层的 P95 下降 4.6% 和 1.8%，有效宽度种数下降 2.2% 和 2.9%。配对中位耗时比为 1.005 和 1.002。新增计时目录的 P95 比为 0.968 和 0.990，两轮均通过 5% 不退化门槛。主门槛要求两轮同时降低 P95 与有效宽度种数至少 5%，并限制配对中位耗时，最终未通过。

逐项配平也使每轮有效宽度与平方和的总量完全相同。有效宽度总和的 P95，从逐项独立的 619、629，在共用一档时升至 944、992，在分层时为 592、599。分层在这台 CPU 和这批输入上缓解了共同长档位的尾部效应，节省的分桶次数也少于共用一档。分层抽样及交换对称化有明确先例，候选贡献是把它们纳入可复核的整窗拒绝合同，并在相同逐题工作量下核验这一取舍。 [原始纳秒记录](audit-runtime-strata-trace.json.gz) · [汇总和分组对照](audit-runtime-strata-results.json) · [查新](audit-runtime-strata-prior.md)
