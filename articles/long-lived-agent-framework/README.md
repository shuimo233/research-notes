# 让个人助手长期工作：AngelBot 的最小记忆与上下文框架

2026-10-30 · 工程研究笔记 · shuimo233

## 摘要

一个个人助手的“长期性”，不是能保存多少聊天记录，而是过了一段时间、换了项目、经历过失败之后，仍能恰当地使用用户的约定，并继续未完成的工作。它既不能每次重放整个档案，也不能把一份不断改写的摘要当作全部真相。

我们在 AngelBot 中探索了一个较小的组合：**完整档案、有界工作视图、带来源的偏好记录，以及同一个 Main 的按需回查**。权限和副作用状态由宿主独立维护，不交给摘要或模型记忆决定。它不训练模型，不增加一组管理记忆的 Agent，也不要求额外的向量服务。

本文整理架构、五组实验和取舍。当前证据支持把这套组合作为继续建设个人助手的最小内核；尚不足以证明自然多日、跨模型和任意任务都长期可靠。机器可读的汇总见 [evidence.json](evidence.json)。

## 1. 我们实际想解决什么

AngelBot 的目标是一个本地优先的 Windows 个人助手。用户只需要面对一个 Main：日常空间处理生活事务，项目空间承载持续工作；工具和子代理在内部协助，而不是让用户管理一组相互割裂的机器人。

长期使用至少有四个不同问题：

1. **记得住**：曾经说过的偏好和约定没有因为摘要、重启或窗口截断而丢失。
2. **找得到**：当前任务需要的信息能从不断增长的资料中被找出。
3. **用得对**：能区分当前约定、历史约定、未来生效和仅本次例外。
4. **接得上**：能分清已经完成、尚未完成、结果未知的操作，恢复后不会重做旧副作用。

“写入记忆成功”只覆盖第一项的一部分。工具存在也不意味着模型会主动使用它；上下文中出现正确原话，也不保证模型会正确判断生效时刻。因此，不能把这四个问题混成一个记忆命中率。

这也解释了为什么不去复刻一套“大模型成长过程”：我们优化的是宿主保存状态、组织输入和核验结果的方式，而不是通过越来越多的反思层去模拟一个新模型。

## 2. 最小架构：四种对象，而不是四套记忆系统

| 对象 | 保存什么 | 何时使用 | 不负责什么 |
| --- | --- | --- | --- |
| 完整档案 | 原始用户消息、回答、必要的私有协议与工具结果来源 | 恢复、回查、纠错 | 不必每轮全部送给模型 |
| 工作视图 | 当前任务、近期交互、可安全整理的完成回合及原件引用 | 每轮输入准备 | 不改写原档，不充当执行权限 |
| 偏好与约定 | 用户原句、来源、作用域、状态和证据 | 当前任务相关时及显式查看时 | 不将推测自动变成用户要求 |
| 执行状态 | 准入、批准、工具结果、未知状态和持久终态 | 每次执行与恢复时 | 不由自由文本摘要裁定完成 |

它们是同一条 Main 链路里的不同职责，不是额外部署的四个服务：

```text
当前请求 + 工作区 + 用户设置
                │
                ▼
        统一上下文准备模块 ◄── 完整档案 / 约定 / 工作视图
                │
                ▼
          同一个 Main ───────► 必要时只读回查原件
                │
                ▼
      既有工具注册表与执行门禁
                │
                ▼
      实际结果核验与原子持久化 ──► 下一轮可回查的档案
```

这条链路复用 AngelBot 已有的 ContextAssembler、工具注册表、协调器和 RunStore。准备输入不创建第二个模型绑定；终态落库也不依赖模型一句“已完成”。

### 2.1 档案与工作视图必须分离

完整保存与完整重放是两回事。已明确结束、结果已知且原件可回查的回合，可以整理成用户原文、最终回答、结果或失败状态，以及封装来源引用。模型需要细节时再读原件。

正在执行的本轮保留完整协议。待确认、结果未知、图片、不支持的旧协议或缺失来源，不通过猜测拼出“半套精简协议”，而是沿用完整历史回退。存储或解码异常则明确报错，不伪装成空历史或成功。

用户编辑或删除消息后，派生摘要和来源可能失效，因此历史选择依赖实际消息父链和来源校验，而不是假设档案永远不可变。明确结束的已知失败可以整理；未知副作用不能因为状态看起来像结束就被压掉。

工作视图减少的是重复传输，不是抹掉失败、删除原件或自动重做。

### 2.2 偏好不等于操作权限

“以后回答先给结论”可以是交流偏好；“现在选另一条路线”是本次要求；“从周五起改用另一方案”带有条件；“以后不必再确认删除文件”则涉及权限，不能当作普通习惯写入后自动扩权。

这些信息可以同时存在，但不能放进一个只保留“最后一句话”的可变摘要里。当前明确输入、作用域及后续更正需要保留，实际操作仍经过宿主门禁。

## 3. 动态约束：保存原话，不制造第二份事实

一个常见的诱惑是把自然语言约定全部拆成规则：偏好值、生效时间、例外条件、优先级和撤回关系，然后让宿主自动裁决。但解析器也会误解语言，字段和冲突规则又会不断膨胀。对当前个人助手目标，我们选择先保留较小的实现。

### 3.1 写入：模型理解，宿主守边界

用户直接表达的稳定偏好，可以由已有学习复盘提出原句；宿主检查它是否真正来自所选 user 消息、是否允许保存、是否属于全局交流偏好，以及是否包含临时、项目、敏感或权限内容。

推测出来的习惯仍作为暂定证据，不能和用户明确说过的话混为一谈。重复证据及相应开关继续生效；用户可以查看、纠正和停用记录。

概念上，一条记录至少要能回答以下问题。这不是新增数据库格式：

```json
{
  "kind": "explicit_preference",
  "scope": "global",
  "quote": "以后工作日挑衬衫，颜色优先深蓝色。",
  "source": "可定位的用户原始消息",
  "source_time": "原始消息时间，而非复盘完成时间",
  "status": "active"
}
```

保存原话并不意味着原话永远正确。新的声明可能撤回旧声明，来源也可能被编辑。保留来源和时序，是为了让这些变化可被重新判断，而不是让宿主假装已经理解所有条件。

### 3.2 读取：有界，但不是只看最近

正式 Main 保留原来的 **12 条工作投影上限**。当偏好数量超过窗口时，根据当前请求选择最多两个候选：

- 一个最强的直接词法匹配；
- 一个匹配候选池中、有效原句来源时间最新的候选；两者相同则去重。

它们只替换窗口内 global 交流偏好的位置，不挤掉本会话约定或其他规则。来源必须仍然是可定位、非 provisional 的 user 消息，并包含所存原句；检查与投影读取处于同一数据库读快照，不提交调用方的事务。

候选池返回上限是 50，但检索仍可能扫描全部合格记录。12、2、50 都是当前实现和证据下的配置，不是对所有模型的最优常数。

词法候选不是语义真值，也不是完整档案。特别是只有字符交集、没有直接匹配的结果，不自动变成任务约定。正式上下文只附带简短宿主元数据：

```json
{
  "selected_candidates": 1,
  "scope": "global_explicit_preferences",
  "complete_archive": false,
  "facts_searched": false
}
```

这避免把“宿主送来了相关原话”说成“所有资料都查完了”。事实、历史、更正关系仍可能需要 Main 回查。新任务重新构建投影，不继承上轮的读取标记。

### 3.3 仍然交给模型的部分

原话中的时间条件、撤回、例外和不同语义之间的关系，仍主要由模型判断。这是当前架构的能力边界，也是评测重点。一次提前采用未来约定的错误，不能靠来源送达来洗掉；但也不应立即触发一套宿主语义规则引擎。

## 4. 怎样评测，才不会把自己测开心

我们把验证分成三层：

1. **确定性合同**：开关、来源、作用域、原子持久化、工作视图回退和恢复不重放。
2. **真实模型诊断**：在合成资料中观察自然请求是否真正使用偏好、是否正确处理时序，以及整个任务的请求和 token 成本。
3. **自然长期使用**：多日真实混合任务、误记和纠正体验、凭据续期、分支和恢复。前两层不能替代第三层。

小样例采用来源绑定评分：正确原话必须实际进入模型输入，或者对应工具调用的结果确实被后续请求读到。答案碰巧猜对、仅展示来源标记、工具只有 success 字样，都不等于使用了证据。

对反事实资料，背景和问题保持不变，只替换偏好内容。这样可以检查答案是否随用户要求变化，而不是依赖模型常识或提示里的暗示。已用于调整实现的题，后续算回归，不再叫独立留出集。

格式规则和别名在调用前冻结；语义合理但不符合该规则的回答，仍保留原严格分数，同时解释失败类型。不事后扩大答案集合追求满分。

成本按完整任务统计，包括回查带来的后续请求。网络失败缺失 usage 时费用为未知，不是零；可用性小探测也不代替业务验收。没有通过不断重试、切换模型或自动转付费接口来填满分数。

## 5. 五组关键观察

以下是内部合成工程诊断，不是 LongMemEval 等官方基准成绩，也不合并成一个“长期可靠率”。精确汇总与限制集中保存在 [evidence.json](evidence.json)。

### E1：轻量工作视图可以减少回放，但恢复语义必须说清楚

六个真实 Main 用户回合覆盖实际写入与读回、更正、长附件、未完成事项、不得发送的约束，以及恢复后的新任务。

| 处理 | 功能回合完成 | 模型请求 | 输入 tokens | 输出 tokens |
| --- | ---: | ---: | ---: | ---: |
| 完整原生协议回放 | 6/6 | 19 | 327,099 | 1,726 |
| 已完成回合轻量工作视图 | 6/6 | 17 | 192,236 | 1,843 |

原生臂虽然功能 6/6，但超过预先设定的 240K 输入资源目标，未通过资源门槛。

观测输入减少约 41.2%。但候选有一次 0 模型、0 工具的准备失败，检查后复用的是候选自身此前已完成且未变的四轮，再接续后两轮，并非从原生基线借用前四轮；它不是两个独立、无中断的新鲜随机 A/B。

两者恢复语义也不同：完整回放跨已完成轮带回原生检查点；轻量视图保留原档，但不回放完成轮的旧 opaque 状态。因此不能把工作视图恢复写成原生协议状态恢复。该结果支持继续采用完成回合投影，不支持宣传通用 41.2% 节省率。

### E2：工具可用，不等于自然请求会查记忆

在两份反事实偏好资料上，最近 12 条、遗漏提示和可用的记忆工具，仍得到 **0/8 的严格来源绑定成功**。答案有一次碰巧猜对，但没有来源支持。

任务相关选择经过一次已知题回归修正后达到 8/8；中间第一次为 6/8。代价是模型请求从 8 增至 15，输入从 22,788 增至 46,435 tokens。

这里得到的是质量与成本的取舍：主动交接相关原话比“工具在那里，模型自己会用”更可靠，但这批结果既不是降耗证据，也不是独立泛化分数。

### E3：窗口更小，端到端反而可能更贵

在衬衫颜色和放松活动两个新主题上，比较 12 条与仅保留前两条的初始视图：

| 初始窗口 | 严格成功 | 请求 | 输入 tokens |
| --- | ---: | ---: | ---: |
| 12 条 | 3/4 | 7 | 20,444 |
| 2 条 | 3/4 | 9 | 23,290 |

2 条版本输入反而高约 13.92%，因为省下的首帧内容没有抵消后续回查。失分包含符合活动偏好、却超出预先冻结别名的回答，未事后改判。

这批数据不支持直接把正式窗口降为 2 条。应该优化完整任务成本，而不是只追求最短 system prompt。

### E4：读取说明有帮助的迹象，但时间条件仍是硬问题

生效前一分钟、到时、撤回、历史、本次例外和未知品牌组成六个边界。原指导与一条“本次已执行有界候选检索”的实验说明配对。

完整完成的五对，两侧都严格正确；请求分别为 10 和 8，输入分别为 31,150 和 24,807 tokens，必要回查仍在。整批却只有 11/12 完成，21 请求中仅 20 次收到 usage。

原指导在生效前一分钟提前采用未来约定；实验说明的对应题连接失败。因而不能推断实验说明解决了时间问题，也不能把五对结果写成完整批次的 100%。该文本替换仍未进入正式 Main。

### E5：接入正式 Main 后，必须区分上下文送达和任务完成

复用真实学习过的合成偏好，加上 61 条噪声，关闭数据库后在另一个项目、零历史的 Main 中接续。实际首帧包含正确原句、12 条窗口、遗漏 50 条及 1 条任务匹配，说明正式装配链已经送达信息。

唯一模型请求随后连接建立失败，没有回答、工具执行或持久完成，也没有 usage。它不是一次成功的真实任务。

对应的离线替身回归覆盖正式准备、回答封存、关库重开和原对话接续；另有开关、来源变更、作用域、受保护窗口及 10,001 条合成记录的检查。这些证明宿主合同，不替模型理解质量背书。

## 6. 当前落地与成本控制

最小内核已经进入 AngelBot 的本地正式 Main 代码，实验层重复的任务选择实现被删除，评测和生产复用同一函数。没有新增记忆数据库、向量服务、后台反思循环或每轮额外模型请求；原有学习复盘与必要压缩仍有各自成本，不意味着整个系统零额外调用。

一个具体的精简点是区分“显式查看”和“自动送入上下文”：手动检索可以返回带 partial 标记的字符级候选；自动投影从不消费它们，就不应先计算字符频率、必要时再扫描一遍，最后把结果丢掉。本轮让它们共用同一个查找核，仅在内部选择是否允许 partial，未扩大公开 Interface 或改动排序、来源和权限合同。

此前 10,001 条合成记录的本机 debug 观察为匹配 179ms、未命中 154ms。这不是 release 基准，更不是恒定耗时承诺；本轮修正减少未使用的工作，不据此声称 token 或答案质量提高。

对不同能力模型，框架能复用的是工具合同、来源、恢复和权限约束。能否恰当地查找、理解更正与条件，仍需分别测试。统一接入厂商并不等于跨模型质量已被验证。

## 7. 从其他实现借鉴什么

相关工作用于解释设计来源，不作为 AngelBot 效果的替代证据：

- [Pi](https://github.com/earendil-works/pi) 强调精简、可扩展的 harness。我们借鉴其小内核取舍，不把每个问题变成新管理层。
- [MemGPT](https://arxiv.org/abs/2310.08560v2) 讨论有限上下文与外部记忆之间的数据移动。档案与工作输入分离可作概念对照，但本文没有复现其论文结果。
- [Hermes 的持久记忆文档](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md) 将有界用户资料、持久记忆与会话检索结合。我们特别区分个人习惯和可复用技能，不把所有经验写入同一种对象。
- [LongMemEval](https://github.com/xiaowu0162/LongMemEval) 将知识更新、时间推理和拒答纳入长期记忆评价。这帮助我们选择诊断维度；本文没有给出其官方成绩，也没有和排行榜横比。

外部链接于 2026-10-30 核验；Pi 旧仓库地址当时已转向上述官方仓库。

## 8. 版本、材料与下一步

实现观察对应 2026-10-30 的本地开发工作树，而非已经全部合并到公开主分支的发行版。AngelBot 当时基准提交为 `390f1d4bdbab1379fa6886cdbca90842b0b5ecfa`，其上包含未合并改动；不能只检出该提交就宣称复现本文实现。

本文公开方法、伪结构、合成案例类别和经核对的聚合清单；没有公开原始 provider 帧、模型私有协议、凭据、个人资料或运行数据库。因此外部读者暂不能从附录独立重算全部历史实验。后续应补齐公开实现的固定提交、可分发的合成输入及评分脚本快照。

在具备对应实现的工作树中，确定性门禁使用 `python scripts/verify.py full`；真实模型和原生桌面验收是单独的显式流程，不能由这条命令代替。正式 Main 的诊断分别核验来源是否真实送达、是否产生实际回答、是否封存结果、重开后是否续接及旧副作用是否重放。

下一步按以下顺序补证据，而不是先堆新层：

1. 连接恢复后完成正式 Main 的真实模型闭环，保留新失败，不循环重跑至通过。
2. 使用新的时间临界点、撤回和仅本次例外，区分已知题回归与独立验证。
3. 进行自然多日混合任务，观察误记、纠正、任务切换、附件增长和凭据续期。
4. 比较不同能力模型及 release 性能，再决定是否需要更复杂的检索。

## 结语

目前最值得保留的结论，不是“某种摘要让模型拥有了永久记忆”，而是一个可维护的分工：**档案负责可追溯，工作视图负责输入成本，来源负责可核对，模型负责语义判断，宿主负责状态与权限。**

这样的框架不保证模型永不犯错，但让错误能够被定位、信息能够被重新读取、已知状态能够在重启后继续，也避免每次遇到漏记就再造一层记忆系统。对一个需要长期相处的个人助手，这比持续扩大 prompt 或追逐单批满分更接近可用的起点。
